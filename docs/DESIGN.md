# 设计文档

本文记录 shushu-s-harmonica 的设计目标、关键约束、架构、算法与取舍，便于后续维护和二次开发。

## 1. 背景与目标

三角洲行动的口琴是单音乐器：自然音键为 `Z X C V B N M ,`，按住鼠标左键降八度、右键升八度、中键升半音，长按可以持续发声；游戏内建的 `R` 自动演奏只覆盖已解锁的曲目。

本项目的目标是：**把任意 MIDI 或简谱转换成这套键鼠输入，在桌面层自动演奏，并保证可随时安全停止。**

成功标准：

1. 键位映射与游戏实际行为完全一致，包括最高音区的特殊规则。
2. 节奏稳定，能够表达连音、断奏和长音。
3. 出现任何异常（失焦、误触、热键占用、输入失败）都不会留下按住的键。
4. 在没有 Windows 的开发机上也能验证曲谱解析、映射与时序。
5. 使用者不需要理解内部实现即可完成选曲、试运行、实机演奏。

## 2. 非目标

- 不注入游戏进程、不读写游戏内存、不修改网络封包、不使用驱动级输入。
- 不做复音/和弦演奏，不模拟多个口琴同时发声。
- 不做音频合成或试听。
- 不自动切换游戏窗口、不模拟点击游戏 UI。
- 不绕过游戏内曲谱解锁机制，仅演奏用户自备的 MIDI/简谱。
- 不保证规避反作弊检测；使用风险由使用者承担。

## 3. 参考实现提炼出的硬约束

设计前对两个开源项目做了对照阅读：

- [ChiZhou6/harmonica-visualizer](https://github.com/ChiZhou6/harmonica-visualizer)
- [lanselanlanxi-wq/HarmonicaPlayer](https://github.com/lanselanlanxi-wq/HarmonicaPlayer)

提炼出的、直接影响本项目的约束：

| 约束 | 来源 | 本项目落地 |
|---|---|---|
| 游戏可用音域为 MIDI 48–85（C3–C#6） | HarmonicaPlayer `HarmonicaPitchMap` | `RANGE_LOW=48`、`RANGE_HIGH=85` |
| 最高音区只支持 `do / #do`：C5 用 `,`，C#5 用 `,`+中键，C6 用 `,`+右键，C#6 用 `,`+右键+中键 | HarmonicaPlayer `GameNoteInput` | `to_action` 对 `pc in (0,1)` 且高八度时特判 |
| 升半音使用下方自然音 + 中键 | HarmonicaPlayer | `_SHARP_BASE` 映射 |
| 音键按下前需 12ms 准备修饰键 | HarmonicaPlayer `GamePlaybackTiming` | `PREP_MS=12` |
| 最短按键保持 40ms | HarmonicaPlayer | `MIN_HOLD_MS=40` |
| 尾隙 20ms（TXT）；MIDI 导入为 10ms | HarmonicaPlayer | 统一取 20ms，见 §15 取舍 |
| 短于 72ms（12+20+40）的音符无法演奏 | HarmonicaPlayer | `build_play_notes` 直接跳过并计数 |
| 按住音键时改变修饰键会重新触发音符 | harmonica-visualizer | 每个音独立包裹修饰键，音键松开后才释放修饰键 |
| 游戏占用大量 F 键，热键需避让 | harmonica-visualizer | 统一使用 `Shift+F8/F9/F10` |

这些参数在本项目中不是硬编码到游戏交互里，而是集中在 `core/mapping.py` 与 `core/engine.py` 顶部，方便后续实机校准。

## 4. 总体架构

```text
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  score.py    │────>│  mapping.py  │────>│  engine.py   │
│ MIDI / TXT   │     │ 音高→按键计划 │     │ 演奏调度线程  │
└──────────────┘     └──────────────┘     └──────┬───────┘
                                                  │
                     ┌────────────────────────────┼────────────────────────────┐
                     ▼                            ▼                            ▼
          ┌────────────────────┐      ┌────────────────────┐      ┌────────────────────┐
          │ input_backend.py   │      │ hotkeys.py         │      │ ui/main_window.py  │
          │ SendInput / DryRun │      │ 全局热键消息循环    │      │ Qt 主线程 + 信号桥  │
          └────────────────────┘      └────────────────────┘      └────────────────────┘
```

分层原则：

1. **解析层不关心游戏**：只输出带绝对时间的 `ScoreEvent`。
2. **映射层不关心时间**：只把音高变成与设备无关的 `PlayNote` 计划。
3. **调度层不关心设备实现**：只依赖 `InputBackend` 抽象。
4. **输入层不关心音乐**：只负责发送扫描码/鼠标事件、前台检测和释放。
5. **UI 层不直接触碰工作线程**：所有回调通过 Qt 信号排队到主线程。

## 5. 数据模型

```python
ScoreEvent(pitch, start, duration, velocity=80)   # 音乐时间的单音事件
Score(name, events, length)                       # 一首曲谱
PlayNote(start, duration, key_index, shift, sharp) # 与设备无关的按键计划
```

- 时间一律使用秒，`start/duration` 为音乐时间（不受暂停影响）。
- `key_index`：0–6 对应 `Z`–`M`，7 对应 `,`。
- `shift`：−1 降八度、0 原调、+1 升八度；负数对应鼠标左键，正数对应右键。
- `sharp`：是否需要中键（升半音）。

## 6. 曲谱层设计

### 6.1 MIDI

- 支持 type 0 / 1；type 2 会抛错（异步轨道无法确定统一时间轴）。
- 跳过 channel 10（index 9，打击乐）。
- `note_on` 且 velocity > 0 为按下；`note_off` 或 velocity = 0 的 `note_on` 为松开。
- 同通道同音高重复按下时先结算前一个音，避免状态覆盖。
- 文件结束时仍未松开的音按 0.5 秒收尾，避免因缺失 `note_off` 丢失旋律。
- 单音化算法：
  1. 按 `(start, -pitch)` 排序；
  2. 开始时间差小于 30ms 的音符归为一簇（容忍人性化演奏和量化误差）；
  3. 每簇取最高音（通常为主旋律）；
  4. 若前一个保留音与当前音重叠，把前一个截断到当前音起点，最短 20ms。
- 选择「最高音」而不是「第一个音」：在主旋律 + 伴奏的常见 MIDI 中，旋律通常位于上方声部。

### 6.2 简谱 TXT

语法（UTF-8）：

```text
TITLE=曲名
BPM=100
GRID=1

[注释 // ...]  音符 token 以空白或 | 分隔
```

- 音符：`1`–`7`，`0` 休止，`8`/`i` 为高音 `do`（音级 1 升八度）。
- 前缀：`b` 降八度（可叠加）、`^` 升八度（可叠加）、`#` 升半音。
- 后缀 `-`：按当前网格延长；单独的 `-` token 延长前一个音符或休止一个网格单位。
- `BPM` 始终表示四分音符速度；`GRID=N`（默认 1，夹在 1–16）把每个 token 的基础时值设为 `1/N` 拍，`GRID=4` 即十六分音符网格。
- 无法识别的 token 会被静默跳过，便于从其他工具粘贴谱面；若整首没有音符则报错。
- `BPM` 非法时回退默认值 100，并夹在 20–300。

### 6.3 图片曲谱转录与节奏重建

`tools/build_from_image_tabs.py` 读取 `data/tabs.json`（逐字转录的音高/八度/分词）与 `data/bpm.json`（参考 BPM 与来源），生成 `scores/图片曲谱/*.txt` 和 `docs/图片曲谱_键位版.md`。

- 原图只编码音高与八度（红=高音、绿=低音、黑=中音），不编码时值；空格分词、逗号和竖线是乐句分隔符，不是音符。
- 节奏按「组内音数决定细分（1 音=四分，2 音按速度取四分/八分，3–8 音=八分，≥9 音=十六分）→ 对齐到 4 个十六分单元的整数倍 → 末音吸收余量」重建，并在句末做延长收束。
- 停顿：逗号 2 个十六分、竖线 4 个、行末 4/8 个（每 4 行或末行加倍），句末延长会抵扣行末休止。
- 参考 BPM 对明显倍速的曲目做折半/还原，理由记录在 `data/bpm.json`。

### 6.4 边界处理

- `TITLE` 为空时使用文件名。
- 文件不存在或编码错误由 Python 异常直接暴露给 UI 日志。
- 曲谱长度按最后一个游标位置计算（包含尾部休止），用于界面时长展示。

## 7. 映射层设计

### 7.1 音高到按键

基础音级：

```text
pc : 0  2  4  5  7  9  11
键 : Z  X  C  V  B  N  M     (index 0–6)
```

八度修饰：

```text
shift = octave − 4          # octave = pitch // 12 − 1（科学音高记号）
shift < 0 → 左键；shift > 0 → 右键
```

升半音：

```text
pc 1 (C#) → Z + 中键      pc 3 (D#) → X + 中键
pc 6 (F#) → V + 中键      pc 8 (G#) → B + 中键
pc 10 (A#) → N + 中键
```

最高音区特判：

```text
if pc in (0, 1) and octave > 4:
    C5  → 逗号
    C#5 → 逗号 + 中键
    C6  → 逗号 + 右键
    C#6 → 逗号 + 右键 + 中键
```

为什么必须特判：如果按通用规则，C6 会变成 `Z + 右键 + 右键`（两个八度），而游戏只有单个八度修饰；参考实现正是用逗号键覆盖最高两个八度。`to_action` 的其余分支保持通用规则。

### 7.2 移调与折叠

1. 自动移调：在 −30 到 +30 半音内搜索，使尽可能多的音高落进 48–85；命中数相同取绝对值更小的移调。复杂度 O(61·N)，对单曲规模足够。
2. 实际移调 = 手动值 + 自动值。
3. 对每个音高先加移调，再按 ±12 折返到 48–85；折返保持音级不变，只改变八度。
4. 丢弃 `duration < 0.072s` 的音符（游戏无法表达），并在返回值中报告数量。

### 7.3 为什么先整体移调再折叠

逐音折叠会破坏旋律的相对音程；整体移调可以保持旋律轮廓。只有少数极端音才需要单独折返，此时至少大部分音符仍保持原调。自动移调让整首曲子「尽量原调」而不是简单粗暴地全部折返。

## 8. 时序与调度层设计

### 8.1 音乐时钟

```text
音乐时间 = perf_counter() − t0 − paused_total
目标时刻 = t0 + paused_total + 音乐时间
```

- `t0` 每轮循环开始时重置（循环播放会重新计时）。
- 暂停开始时记录 `pause_begin`，恢复时把暂停时长累加到 `paused_total`，因此恢复后不会「追赶」错过的音符。
- 调度等待粒度为 5ms；Windows 输入后端额外调用 `timeBeginPeriod(1)` 提升定时器精度。

### 8.2 单音时序

```text
按下修饰键（若有）
等待 PREP_MS = 12ms（期间可被停止打断）
按下音键
release_at = max(start + duration − 20ms, now_music + 40ms)
等待到 release_at（期间处理暂停/失焦/停止）
松开音键
按相反顺序松开修饰键
```

- `now_music` 在音键按下后计算，所以 `MIN_HOLD` 是对实际按住时长的兜底。
- 每个音符结束都释放修饰键，避免在按住音键时改变修饰键触发重新发声。
- `finally` 块保证任何异常路径都会尝试松开音键和修饰键。
- 停止/暂停时 `release_all()` 由调度线程和 UI 线程共同兜底，但输入后端只释放自己记录为按下的键。

### 8.3 状态机

```text
idle ──play──> countdown ──> playing ──finish──> finished ──> idle
                                 │  ↑
                         失焦    ▼  │ 恢复
                            waiting_game
                                 │  ↑
                         手动暂停 ▼  │ 继续
                              paused
任意活动状态 ──stop/急停/异常──> idle（释放所有输入）
```

- 状态变化通过回调推送到 UI，UI 依据状态启停按钮。
- `countdown` 期间停止会立即取消，不会留下按键。
- 失焦与手动暂停共用暂停逻辑：释放按键、冻结音乐时钟、状态提示。

### 8.4 进度与日志

- 每个音符开始前回调 `(index, total, note)`，UI 显示「第 i/N 音 · 按 X（修饰）」。
- 日志覆盖：环境与权限、热键注册结果、移调统计、跳过音符数、暂停原因、结束/停止/错误。

## 9. 输入层设计

### 9.1 SendInput

- 键盘：只发送扫描码，`KEYEVENTF_SCANCODE`，按下/松开分别不带/带 `KEYEVENTF_KEYUP`。扫描码比虚拟键更接近物理键盘，兼容性更好。
- 鼠标：按下/松开使用 `MOUSEEVENTF_LEFTDOWN/UP`、`RIGHTDOWN/UP`、`MIDDLEDOWN/UP`。
- 每次调用 `SendInput` 必须返回 1，否则抛出带排查建议的 `RuntimeError`（权限不一致、输入法、窗口模式）。
- 使用 `ctypes` 直接声明结构体和 `argtypes`，不依赖 `pywin32` 等第三方库。

### 9.2 按键跟踪与释放

- `Win32Backend` 维护 `_held_keys` 与 `_held_buttons`。
- `release_all()` 只释放自己记录为按下的键，避免误松开用户手动按住的键。
- 松开失败时保留记录，允许后续再次尝试。

### 9.3 前台检测

```text
GetForegroundWindow
  → GetWindowThreadProcessId
  → OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)
  → QueryFullProcessImageNameW
  → basename
```

- 与「游戏进程关键字」做不区分大小写的子串匹配，适配不同客户端命名。
- 调度线程以 150ms 缓存轮询结果，避免每 5ms 都做系统调用。
- UI 每秒刷新一次前台进程显示，便于排查关键字配置。

### 9.4 DryRun

- `DryRunBackend` 所有输入方法为空操作。
- 非 Windows 平台强制使用；Windows 上可手动勾选「仅测试」。
- 用途：验证曲谱解析、映射、时序、UI 状态机，不接触游戏。

## 10. 安全设计

威胁与对策：

| 风险 | 对策 |
|---|---|
| 用户点播放后还没切回游戏就开始按键 | 3 秒倒计时 |
| 演奏中切出游戏导致按键落到其他窗口 | 仅前台检测，失焦立即释放并暂停 |
| 程序异常/停止时按键卡住 | `finally` 释放 + 后端跟踪集合 + 暂停/停止主动释放 |
| 急停热键被占用，用户无法停止 | 启动后校验；`Shift+F8` 注册失败则禁止真实演奏 |
| 误在开发机/无游戏环境发送按键 | 非 Windows 强制 DryRun；Windows 可手动仅测试 |
| 权限不一致导致 SendInput 静默失败 | 启动显示权限；失败时抛出带提示的错误 |
| 热键抢占游戏按键 | 全部使用 Shift 前缀 + `MOD_NOREPEAT` |
| 退出程序留下按键 | `closeEvent` 停止播放并释放所有输入 |

边界说明：如果进程被强制杀死（任务管理器/崩溃），Windows 不会自动替应用发送 keyup，可能留下逻辑按下的键；此时手动按一下对应键或切出游戏即可恢复。这是所有模拟输入方案的共同限制。

## 11. 热键设计

- 使用 `RegisterHotKey(NULL, id, MOD_SHIFT | MOD_NOREPEAT, vk)`，注册到独立线程的消息队列。
- 线程启动时先 `PeekMessage` 创建队列，再 `GetMessage` 循环分发 `WM_HOTKEY`。
- 退出时通过 `PostThreadMessage(WM_QUIT)` 结束循环并注销热键。
- 回调只发出 Qt 信号，实际处理在主线程，避免跨线程 UI 操作。
- 失败列表暴露给 UI；启动 700ms 后统一报告注册结果。

选择 `Shift+F9/F10/F8` 的原因：

1. 避开游戏常用的 `F1`–`F12` 单键和 `Alt` 组合；
2. 三键分布在键盘左侧，单手可及；
3. 不与常见输入法切换冲突（`Shift` 单独切换输入法不会触发组合键）。

## 12. UI 设计

- 单窗口、左侧曲库、右侧控制/安全/日志三块，状态栏显示运行环境。
- 所有耗时操作（解析、演奏）不在 UI 线程执行；解析在点击时同步执行（单曲规模小），演奏在独立线程。
- 按钮启用规则与状态机绑定：演奏中禁用「播放」，活动状态启用「停止」，仅 playing/waiting_game/paused 启用「暂停」。
- 曲谱信息实时反映手动移调/自动适配结果。
- 深色 QSS，突出主操作按钮和当前状态颜色。
- 冻结（PyInstaller）时曲库目录取 exe 所在目录的 `scores/`，避免写入临时解包目录。

## 13. 打包

`build_exe.bat`：

```bat
python -m pip install -r requirements.txt pyinstaller
python -m PyInstaller --noconfirm --clean --windowed --name HarmonicaPlayer main.py
xcopy /E /I /Y scores dist\HarmonicaPlayer\scores
```

- `--windowed`：不显示控制台；日志在 UI 内。
- 默认 one-folder 模式，升级/替换资源方便。
- `scores/` 放在 exe 同级目录，用户可自由增删曲谱。
- 冻结判断：`getattr(sys, 'frozen', False)` 时使用 `Path(sys.executable).parent / 'scores'`。

## 14. 测试策略与记录

由于真实输入依赖 Windows，本项目采用「设备无关核心 + 记录型后端 + 离屏 GUI」的测试策略。

### 14.1 核心自测（macOS 3.9.6 / PySide6 6.10.3 / mido）

- 解析：`scores/twinkle.mid` 得到 42 个音，`scores/小星星.txt` 得到 56 个音。
- 映射边界断言：48/49/60/61/71/72/73/74/76/83/84/85 → `(key_index, shift, sharp)` 全部符合上表。
- 过短音符：50ms 音符被丢弃，`dropped=1`。
- 时序（记录型后端，3 个音）：
  - keydown 误差 ≤ 0.2ms，keyup 误差 ≤ 0.4ms；
  - 459ms 音符实际保持 428ms（459 − 20 − 12 = 427ms，实测 428ms）。
- 前台失焦：演奏中失焦进入 `waiting_game`，恢复后继续并完成，暂停 0.4s 后总时长 3.34s。
- 手动暂停：状态序列 `playing → paused → playing → finished → idle`。
- 循环 + 停止：2 个音循环播放 1.6s，按键按下/松开次数相等，停止后状态 `idle`。
- 整曲 DryRun：MIDI 42 音在 20 倍速下 2.25s 完成；TXT 56 音正常完成。

## 15. 设计取舍

1. **统一尾隙 20ms**：参考实现中 TXT 默认 20ms、MIDI 导入 10ms。本项目为降低维护复杂度与保证不粘连，统一取 20ms；如实机需要更连奏，可把 `DEFAULT_GAP_MS` 调小并重新验证最短时长。
2. **高层单音化而非轨道选择**：MVP 优先「任意 MIDI 能直接弹」，用最高音启发式近似主旋律；后续可增加轨道选择或旋律检测。
3. **整体移调优于逐音折叠**：保持旋律轮廓，减少八度跳变；代价是整体可能升降调。
4. **ctypes 手写 SendInput**：依赖少、行为透明，也不引入第三方输入库；代价是需要自行维护结构体定义。
5. **PySide6 而非 tkinter**：需要深色主题、状态栏、日志面板和更接近原生桌面工具的观感；代价是打包体积较大。
6. **Shift 前缀热键**：牺牲一点按键便利性，换取与游戏按键的低冲突概率。
7. **急停热键注册失败即禁止演奏**：牺牲极端情况下的可用性，换取「一定能停下来」的安全保证。
8. **固定 3 秒倒计时**：实现简单、可预期；后续可做成设置项。
